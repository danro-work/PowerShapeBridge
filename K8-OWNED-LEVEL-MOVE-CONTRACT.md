# К8 — перенос собственного объекта на другой слой

Статус: внутренняя подготовка и повторная проверка плана реализованы;
40 isolated cases / 10 controls / 30 refusals и independent audit1177hashchecks
passed. Общая проверка sourceSDK39.8/native34.5 завершилась успешно:
678.NET/531native/175compatibility/Inspector; evidence/K8-level-move-sdk-final.
Исполнение, публичный MCP-инструмент и живая квалификация ещё не реализованы.
Этот документ не разрешает изменение CAD.

## Первый принимаемый сценарий

Одна собственная тестовая копия, один SOLID и один явно указанный существующий
именованный слой назначения. Операция меняет принадлежность объекта слою.
Положение и геометрия остаются прежними. Имя, видимость и фильтры слоёв не меняются.
Целевой слой задаётся пользователем/планом; автоматический выбор свободного слота
не используется. Слои 998/999, предназначенные для построений, исключены из
первого сценария. Перенос нескольких объектов принимается следующим блоком.

`SetItemsLevel(composite_id, level_number)` документирован в установленном
PowerShape 2023: номер 0–999, результат BOOL; вызов снимает выделение и может
создать безымянный слой, если назначенный слой не существует. Поэтому успешное
чтение USED=0 не является основанием для автоматического создания/использования.
Даже BOOL=true требует независимой проверки принадлежности объекта слою.

API-источник: `C:\Program Files\Autodesk\PowerShape 2023\file\ole\data\IPshapeModelDoc.htm`,
раздел `SetItemsLevel`. Официальная справка [Level dialog](https://help.autodesk.com/view/PWRS/2023/ENU/?guid=GUID-4FABEC7F-C998-4624-97B3-5597E2EA0AAA)
описывает 1000 слоёв, встроенные слои 0–4, construction998/999 и зависимость
видимости от model/window/view. Это не API проверки владения объектом или слоем.

## План и подготовка

План содержит ID/SHA владения копией, независимый checkpoint, binding ID/SHA,
entity-set ID/SHA, исходную inspection ID/SHA, receipt слоёв ID/SHA,
короткий срок действия и точную пару native type/id. Native composite ID
получается заново из текущего `GetModelItems`/`GetItemData`; ранее прочитанный
composite не используется без текущего сопоставления.

Параметры: `targetLevelNumber`, ожидаемые имя и raw-флаг активности этого слоя,
`selectionAfterPolicy=cleared_by_documented_api`, `mode=move_in_place`.
Тело уже на целевом слое отклоняется как отсутствие изменения.
Подготовка не вызывает SetItemsLevel, не меняет выделение и выдаёт
`executionEnabled=false`, `nativeProviderQualified=false` до приёмки провайдера.
Сейчас доступна только внутренняя `OwnedLevelMovePlans.Check`: режимы
prepare и revalidate, receipt/plan SHA, retained proofs, два native level scans
до и после публикации, journal только prepared. Нет production COM entry point,
queue recipe или публичного SDK tool. Default full/read-only catalogs сохранены.

Перед публикацией плана нужны свежие stable model/process/window observations,
полное покрытие native inventory, два совпадающих чтения слоёв, отсутствие
неразрешённого mutation/export fence и совпадение всех удерживаемых доказательств.
Сохранённый рабочий файл проверяется с учётом уже открытого CAD writer;
checkpoint/source остаются защищены. Не применять несовместимый FileShare.Read
к текущему рабочему файлу. Изменение EOF/mapped bytes контролируется SHA/length,
а не объявляется невозможным из-за byte lock.

## Исполнение

Только полный сервер; отдельное разрешение на конкретный live тест.
После свежей проверки контекста — durable once claim, mutation fence,
`command_started`, один SetItemsLevel для точно сопоставленного объекта.
Не добавлять скрытые ShowLevel/SelectItem/SetLevelName/сохранение/активацию.
Ожидаемое снятие выделения явно показывается пользователю до разрешения.

При исключении, BOOL=false или несовпадении проверки исход считается неизвестным
до независимого разбора. Автоматический retry, перенос обратно и снятие fence
запрещены. BOOL=true сам по себе не завершает журнал успешным состоянием.

## Независимая проверка

Новый retained read context должен подтвердить ту же собственную модель,
процесс и комплект окон; единственный выбранный target перешёл на целевой слой;
type/id/name и остальные объекты не изменились; slot names/active/filter flags
сохранились; выделение снято, workplane не изменён. USED может измениться на
исходном/целевом слоях из-за переноса — это ожидаемый эффект, а не ошибка.
Bounds и доступные свойства сравниваются как наблюдения, не полная топология.

Сохранение в новый owned target и reopen требуют своего заранее объявленного
сценария; команда переноса не сохраняет автоматически. После reopen отдельно
подтверждается принадлежность объекта слою. Разрешённое успешное завершение
журнала и release fence возможны только после принятой независимой проверки.

## Что пользователь проверяет

1. План показывает точный объект, исходный/целевой слои и снятие выделения.
2. В отчёте один вызов SetItemsLevel и сохранность посторонних объектов/окон.
3. Объект действительно находится на нужном слое при повторном чтении.
4. При отдельном save/reopen слой сохранён; checkpoint/source не затронуты.
5. Fault cases сохраняют неизвестный исход и запрет повторного исполнения.

Не закрывает общую К8: batch transfer, создание/переименование слоёв,
управление выделением и workplanes принимаются отдельно. К9–К11 обязательны.

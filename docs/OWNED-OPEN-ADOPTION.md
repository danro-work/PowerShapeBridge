# Current owned document after an interrupted OPEN

`ownedOpenAdoptionExperimental` defaults to false and requires the guarded owned OPEN/copy/candidate/binding features. The full SDK explicitly registers `OwnedOpenAdoptionTools.Create(session)` in `ToolCatalog`. The read-only server excludes both tools and keeps its existing eight tools.

`adopt_owned_open_document` accepts the exact original OPEN request, terminal timeout response SHA, frozen plan SHA, and fresh candidate/one-use active listing choice. Its Native route supports exactly the three-event `prepared → execution_claimed → command_started` journal with a terminal worker timeout. It holds the original request, plan, receipts, claim and chain, rejects an existing original worker or queued request, and checks the original before-window inventory against exactly one new current active owned window. It checks retained COM document identity, two current observations, WORLD/empty selection, ownership/source/checkpoint/current initial working bytes, and absence of mutation/export fences. Current saved-file hashes are compared across this observation.

A real Native context can freeze a separate adoption report and a once record, returning `owned_open_document_adopted_observed`. A fake context returns an unqualified observation and cannot create the authority once record. The SDK independently checks the raw receipt, report, original chain, claim and once links before issuing a connection-local working-copy lease. The lease still requires normal fresh binding/set/operation preparation before a later edit.

The original OPEN response, three-event journal and open-once claim remain unchanged. In particular, adoption does not insert `command_returned`, append historical success, replay OPEN, remove a fence, or assert full topology. `originalCommandReturned`, `originalJournalModified`, `historicalSavedBytesCertified` and `fullTopologyEquivalent` are false. The old frozen OPEN plan does not contain a durable complete saved-hashes-before snapshot, so adoption cannot certify that missing historical comparison.

`restore_owned_open_adoption` provides explicit reconnect validation after an initial adoption was confirmed but its connection-local lease expired. It accepts that initial successful adoption request/receipt SHA and fresh candidate/active choice. It validates the initial report/once links, repeats the current retained-document and file checks, then freezes a distinct current observation report (`owned_open_adoption_refreshed_observed`). The initial adoption once record and OPEN journal remain unchanged. A refresh or unknown result cannot stand in for the initial successful adoption. This is current access validation, with no CAD command.

Both tools consume the active choice before submission. Cancellation/timeout after submission is unknown local-artifact state and never triggers automatic retry or a new lease. A partial report or once write must be inspected before any subsequent action. The Native route serializes through the existing executor lock; it never repairs another writer or claim.

The current scope requires the original initial working disk bytes and the same process/window inventory; it is not generic recovery for arbitrary edits, SaveAs, replacement documents or process restart. It checks observed current geometry consistency without proving that no earlier unsaved edit occurred. A later operation must pin and independently verify its own observed source.

Scale preparation now uses the existing shared `OwnedWorkingBytePin` so an already-open PowerShape writer handle is compatible while ordinary writes to supported data bytes are blocked. Retained identity/length/SHA checks remain necessary: Windows mapped writes and EOF changes are not universally prevented by range locks. The checkpoint stays independently held and read-only. The new writer-handle regression reproduces the former sharing refusal without connecting to CAD.

The SDK's passive working-file byte check permits that existing writer and hashes the retained stream twice with stable length; it denies replacement and leaves the checkpoint sharing strict. This is byte correlation with the Native receipt, not an execution lock. The later Native executor still holds its own byte pin and ownership/context guards. The qualified scale wrapper preserves the passive preparation's completed four-read receipt and records its additional guards separately, so extra checks cannot overwrite the earlier contract. SDK validation of that passive contract remains strict.

Validation: targeted Native interrupted-chain/fake-provider/foreign-choice/fence/source-byte guards, SDK flag/read-only/schema/receipt-chain/reconnect tests, actual staged STDIO discovery and an early real owned-copy scenario. Current live qualification and limitations are recorded in `PROJECT-STATE.md` and the local state card; synthetic success alone does not qualify a real scale or saved-result workflow.
